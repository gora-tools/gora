## Context

Milestone 3 (ADR-009) is a hard gate: GORA must release itself using its own release
engine. To do that deterministically we must fix how the release artifact is produced,
what GORA's own release stages are, how the artifact digest flows into the manifest,
whether artifacts are signed, and where the automation boundary sits.

Constraints from existing ADRs:

- ADR-002 — deterministic code owns sequencing; no unrestricted model-to-system execution.
- ADR-003 — the artifact digest is the release identity; the version tag is human-facing.
- ADR-004 — promotion preserves digest identity and follows a linear path per release line.

  *Amended 2026-10-09 (ADR-024 section 1):* there is no release line; ADR-004 holds linearity
  per artifact, by the order of promotion and by moving only forward.
- ADR-005 — stack is GitHub Actions, Docker, cosign; container registry is GHCR.

  *Amended 2026-10-08 (correction):* ADR-005 names GitHub Actions and Docker; cosign and GHCR
  are this ADR's choice.
- ADR-007 — no premature orchestration; favour synchronous, operator-driven steps first.

## Decision

### Artifact and registry

The release artifact is the GORA container image built from
`deployments/docker/Dockerfile`, published to GHCR at
`ghcr.io/gora-tools/gora`. Release identity is the image **digest** (`sha256:…`),
per ADR-003. The semantic version tag (e.g. `0.2.0-rc.1`, `0.2.0`) is human-facing only.

### Trigger

The release workflow triggers on a pushed git tag matching `v*` (e.g. `v0.2.0-rc.1`,
`v0.2.0`) — a tag is the explicit release-identity event. The existing CI workflow
(lint/format/type/test) continues to run on push/PR to `main` and is unchanged.

*Superseded 2026-10-02 (see Amendments and ADR-018 section 7):* only a release-candidate tag
(`v0.2.0-rc.1`) builds; a final tag such as `v0.2.0` never builds, the final release is a retag
of the verified candidate digest.

*Amended 2026-10-03 (ADR-022):* the build runs on a commit to `main` that changed GORA's inputs;
GORA verifies it and creates the rc tag on that commit. Until registration is implemented, the
operator pushes the rc tag and the tag starts the build.

*Amended 2026-10-10:* see the note of 2026-10-10 under "Digest flow".

### Signed OCI artifacts (SBOM + provenance + signature)

Every published image is a **signed, attested OCI artifact**, not just a container.
Three things are produced at publish time and bound to the image **digest**:

- **SBOM** — generated with `syft` (SPDX or CycloneDX) and attached as a cosign
  attestation, so the contents of the artifact are inspectable.
- **Provenance** — SLSA build provenance generated by BuildKit at build time
  (docker/build-push-action `provenance: mode=max`) and stored as an OCI attestation
  in the registry — no platform-proprietary attestations API — so *how* and *from what
  commit* the image was built is verifiable.
- **Signature** — the image is signed with **cosign keyless** (OIDC via the Actions
  `id-token`).

*Amended 2026-10-08 (correction, ADR-018):* the SBOM is CycloneDX, and signed provenance comes
from GitHub artifact attestations run from a reusable workflow; see Amendments.

*Amended 2026-10-09 (ADR-027 section 7):* GitHub artifact attestations need GitHub Enterprise Cloud
in a private repository, so GORA's own provenance and SBOM will be attested with `cosign` from a
reusable release workflow; GORA verifies the statement and its signer, whichever tool made it.

*Amended 2026-10-10 (ADR-027 sections 7 and 8):* the repository is public since 2026-10-10, so
the reason above, Enterprise Cloud for a private repository, no longer applies. `cosign` stays:
GORA depends on no host's tool or plan (ADR-027 section 7).

*Amended 2026-10-19 (ADR-018 section 3):* the predicate GORA's own workflow signs is
`workflow/v1`, made from the claims of the run's OIDC token as GitHub's toolkit makes it,
since GORA's evidence check refuses any other form; the tool that writes it is chosen with
that workflow.

All three are verifiable from the digest alone (`cosign verify`,
`cosign verify-attestation`). This makes GORA's own release identity not only
immutable (digest) but *trustworthy* (signed + attested) from the first
self-release — matching the ADR-005 stack and the target of signed OCI artifacts
(cosign + SBOM + provenance). SBOM and provenance are built fresh here; there is no
reusable prior-art for them (see `docs/reference/prior-art-bom-poc.md`, which covers
the promotion model only).

*Amended 2026-10-08 (correction):* the stack this paragraph matches is this ADR's; ADR-005 names
GitHub Actions and Docker, not cosign (see "Constraints from existing ADRs").

### GORA's own stages

Stages are **environment-style and start with `dev`** — GORA's self-manifest reflects
the real promotion mechanism from day one rather than a symbolic candidate→released
shortcut. The promotion graph is linear (ADR-004) and extends to further environments
(e.g. `prod`) as GORA gains real runtime targets; AWS is the planned cloud for GORA.
Promotion moves the same digest across stages — no rebuild.

*Amended 2026-10-08 (ADR-024 section 9):* GORA's stages are `dev` (`auto`), `staging`
(`approval`) and `prod` (`approval`). GORA's release pipeline runs the version `prod` holds; the
final tag `vX.Y.Z` is created when a version enters `prod`.

### Digest flow and automation boundary (ADR-007)

- CI **produces** the immutable, signed artifact and surfaces its digest (job output /
  step summary). CI does **not** mutate the manifest in M3.
- An operator — or the delegated Claude Code agent — records and promotes via the CLI:

  ```bash
  gora cut-rc --image ghcr.io/gora-tools/gora --version <v> --digest <sha256 from CI>
  gora promote dev
  # commit the updated release-manifest.yaml  (Git = source of truth)
  ```

- Fully automated `cut-rc` + promotion PRs (CI/agent-driven) are explicitly **deferred to
  Milestone 4** (GitHub adapter, ADR-006). M3 stays CLI-driven and deterministic.

*Amended 2026-10-08 (ADR-019 section 2, ADR-023 section 2):* the manifest is never committed by
hand: it changes only through a pull request whose content GORA computed, and until GORA opens
it, the operator opens it from an ordinary branch. Registration replaces `cut-rc`.

*Amended 2026-10-10 (ADR-026 section 16):* this procedure ended with manifest v0.1: `cut-rc`
and `promote` are removed, and no version tag is pushed by hand any more, since only GORA
creates them (L10). Registration and the stage loop replace it (ADR-023 section 2).

*Amended 2026-10-11 (ADR-022 section 14):* GORA's identity on GitHub is the GitHub App
`gora-release` (the name `gora` was taken), acting as `gora-release[bot]`. The organization
`gora-tools` owns it, and it is installed on this repository alone, with read and write on
contents, pull requests and commit statuses, read on metadata, nothing else, and no webhook.
Its id and private key are a variable and a secret of the environment `gora`, whose deployment
branches are `main` alone; a workflow mints an installation token for one run with
`actions/create-github-app-token`. The rulesets `release-tags-creation` and
`state-tags-creation` let it alone create `v*` and `prod/*` tags, `gora-branches` lets it alone
create, update and delete `gora/**` branches, and `protect-release-tags` and
`protect-state-tags` let no one, the App included, update or delete a tag. The organization
permission "Members: read" is added with the first check of who may ask or approve.

### Self-manifest

`release-manifest.yaml` (schema v0.1) lives at the repo root — GORA's own release
contract, managed by GORA's own engine.

*Amended 2026-10-09 (ADR-026 section 16):* GORA's own release files are those of any project:
`release-policy.yaml`, `artifacts/gora/artifact.yaml`, `.github/CODEOWNERS`, and the `state/` and
`rejections/` trees GORA writes. The pull request that adds them deletes `release-manifest.yaml`,
whose history stays in Git, and carries no entry over: the first state file is the first
promotion of `0.2.1-rc` into `dev`.

## Consequences

- GORA dogfoods its own contract: `cut-rc`/`promote` operate on GORA's real published
  digest, validating the entire release model — the M3 exit criterion.

  *Amended 2026-10-08 (correction, ADR-009):* the exit of Milestone 3 is restated in the model
  of ADR-024: `gora register` and the stage loop promote a version of GORA into `prod`.
- Two GitHub Actions workflows: the existing CI (lint/test) and a new release workflow
  (build → sign → push) gated on `v*` tags.

  *Amended 2026-10-08 (correction, ADR-022):* the build moves to a commit on `main`; see
  Amendments.
- Signed OCI artifacts require GHCR + OIDC permissions on the release job
  (`packages: write`, `id-token: write`), plus `syft` and `cosign` available in the
  workflow. Provenance is registry-native (BuildKit), so no `attestations: write`
  permission or GitHub attestations API is needed.

  *Amended 2026-10-08 (correction, ADR-018):* signed provenance uses GitHub artifact
  attestations; see Amendments.
- The `dev`-first environment model lets the promotion graph grow with real environments
  (AWS) instead of being retrofitted later.
- Manifest updates stay human/agent-initiated in M3; automation is a deliberate M4 step,
  preserving ADR-007. *Amended 2026-10-08 (ADR-023 sections 7 and 8):* every manifest change is
  a GORA pull request merged by the host's auto-merge; see "Digest flow".
- **ADR numbering:** this ADR takes 011; the planned Project Intelligence / ADR Sync ADR
  becomes ADR-020. *Amended 2026-10-08 (correction):* ADR-020 is reserved for it; it is not
  scheduled (the workflow catalog).

## Connectors (context, not scope)

GitHub and Slack are the first integration targets; Bitbucket and others follow later.
These are adapter concerns (ADR-006) and out of scope for the M3 self-release pipeline.

## Amendments

### 2026-10-02 — trust model decided in ADR-018

What this ADR built is a signed image with attached evidence; what it does not yet give is a
*verified* release. Corrections, decided in ADR-018:

- The BuildKit provenance described above is **not signed**: SLSA Build L1 at most. Signed
  provenance moves to GitHub artifact attestations (`actions/attest`) run from a reusable
  workflow, SLSA Build L3, stored in the registry (`push-to-registry`). The sentence "no
  platform-proprietary attestations API" is superseded: the attestation is a standard in-toto
  statement in the registry, and verification does not call the GitHub API.
- The SBOM format becomes **CycloneDX 1.6** (replacing SPDX), one per image.
- The verify step matches the signer by **exact identity**, not by regular expression.
- "Trustworthy from the first self-release" holds only once GORA verifies the evidence before
  `cut-rc` (ADR-018 section 4). Until then the image is signed, not verified.

### 2026-10-02 — the image is immutable at run time; a build only for a candidate

- The image's entrypoint is `uv run gora`, which synchronises the virtual environment every
  time the container starts (it installs the project on each start). A released artifact must
  not change itself at run time: the same digest must behave the same, offline, and with a
  read-only root filesystem (the usual Kubernetes setting). The entrypoint runs the CLI already
  installed in the image's virtual environment, with no sync and no network.
- The release workflow builds only for a release-candidate tag (`v<version>` with a
  pre-release part). A final version is never built; it is a retag of the verified candidate
  digest, performed by GORA after the final promotion pull request is merged (ADR-018
  section 7).

### 2026-10-03 — two platforms, built on native runners

ADR-021: the release image is one OCI image index for `linux/amd64` and `linux/arm64`. Each
platform is built and smoke-tested on its own native runner and pushed by digest; a final job
assembles the index, whose digest is the release identity. Signature, provenance and SBOM
cover the index and each platform manifest (ADR-018 section 2, amended). No build runs under
emulation, and a release image is built only by this workflow, never on a developer's machine.

### 2026-10-03 — the build follows `main`; GORA creates the tag

ADR-022 makes every merge to `main` that changes an artifact's inputs a candidate. The release
workflow will build on that commit, once, and GORA will register the candidate: compute the
version, create the annotated tag `vX.Y.Z-rc.N` on the source commit, and add the registry tag.
A tag will no longer start a build. Until registration exists, the operator pushes the rc tag
by hand and the tag starts the build; the tags pushed so far stay valid.

### 2026-10-08 — GORA's own stages; the final tag on entering `prod`

ADR-024 decides the versions and the order of promotion. GORA's stages are `dev`, `staging` and
`prod`, and GORA's release pipeline runs the version `prod` holds; a candidate's version is
`X.Y.Z-rc`, and the final tag `vX.Y.Z` is created when the version enters `prod`. The rc tags
`v0.2.0-rc.1` to `v0.2.0-rc.6` are not candidates of the model; GORA's policy declares the
initial version `0.2.1`, which orders after them (ADR-024 section 9). The section "Digest
flow" also gains a pointer to ADR-019 section 2 and ADR-023: the manifest changes only through a
pull request, and registration replaces `cut-rc`.

*Amended 2026-10-22 (correction, ADR-024 section 9):* the initial version is written `0.2.1-rc`, as
ADR-024's amendment of 2026-10-16 says of this entry.

### 2026-10-08 — the ADR-005 stack, the Milestone 3 exit, ADR-020 reserved

A correction: ADR-005 names GitHub Actions and Docker, not cosign or GHCR; the exit of Milestone
3 is the one restated in ADR-009; ADR-020 is a reserved number, not a scheduled ADR.

### 2026-10-20 — the release image carries git, from one Debian snapshot

GORA reads a repository's content with git (ADR-006, Git adapter), so the release image
carries it. The base stays the Docker Official Image `python` on Debian, by the digest of
its index, its tag naming the Debian release (`python:3.12-slim-trixie`): glibc, the wheels
`uv.lock` pins, both platforms, Debian's security process. Without the codename a digest
bump would move the image to the next Debian release unseen. Weighed on 2026-10-20 and not
taken: Docker Hardened Images (Python 3.12 and git on Debian 13, signed provenance, free
since 2025-12; its runtime has no shell and no apt, so git and its libraries would be
carried across stages; to be revisited), Chainguard (an exact 3.12 only on a paid plan),
distroless (no 3.12, no git), Alpine (musl: every wheel changes), and Python from
python-build-standalone on `debian` (its bundled libraries are patched outside Debian's
security process).

The packages come from one snapshot of the Debian archive, which replaces the base's sources:
`deployments/docker/debian.sources` names `snapshot.debian.org` for `trixie` and
`trixie-updates`, and for `trixie-security`, each at the import it was taken from, and
`deployments/docker/debian.lock` pins the SHA-256 of each Release file (`InRelease`) that
snapshot serves; both are inputs of the artifact (L8; *amended 2026-11-07:* they are not, since
the release image installs nothing, see the entry of that date). A time names the latest
import before it that the archive holds when it is asked, so a time in the future would name
another import later; and `snapshot.debian.org` serves every file by a redirect to its content address
(`/file/<sha1>`), so apt cannot tell an exact import from a time. The lock can: after
`apt-get update` the build compares the Release files apt fetched, their signatures checked,
with the lock, and any other set fails the build. A Release file holds the hashes of the
package indices, and they the hashes of the packages, which apt checks as it downloads them:
the base digest, the lock and `GIT_VERSION` fix every package the install brings, and the same
commit installs the same packages for as long as the base digest and the snapshot are served.
The build depends on `snapshot.debian.org` as it depends on PyPI for `uv.lock`. `apt-get
update` fails on any error, so a snapshot that is unreachable, or reachable in part, fails the
build, which never falls back to the live archive; the build refuses any other apt source. A
snapshot's Release files are past their `Valid-Until` by design, so that date is not checked;
their signatures are, with the base's Debian keyring. `GIT_VERSION` asserts the version the
snapshot holds, and `make image-smoke` checks the installed package and `git --version` against
it, read-only and offline (TESTING rule 3).

Freshness is decided here and not built (release-model section 13); until it is, the
snapshot, its lock and `GIT_VERSION` move by hand, together, in one pull request.

*Amended 2026-11-05:* the build that depends on `snapshot.debian.org`, and on Docker Hub for
the `python` base, is the build of GORA's own base image, below, which a person runs when the
base must change. The release image starts from that image once the pull request that says so
is merged; until then it installs git as this entry describes.

*Amended 2026-11-07:* the release image starts from that image, so it installs nothing; this
entry now describes how the base is built. The snapshot, its lock and `GIT_VERSION` move
together in the base's pull request, and a person then runs `base.yml` and moves the digest.

- **The image scan.** Grype scans the release image of every pull request and fails on a
  vulnerability that has a fix and is of high or critical severity. An exception names the
  vulnerability, the package, the reason and the date it expires, and a test fails on one
  past that date: Grype's ignore rules carry no date. A scheduled run scans `main` and the
  latest release. GitHub notifies the user who last changed a scheduled workflow's cron
  schedule, and disables a public repository's scheduled workflows after 60 days without
  activity; the pull request that builds the scan says how each is met. The same tool
  scans `uv.lock`. Trivy was weighed: its ignore file with an expiry date is experimental,
  and its releases and actions were compromised in March 2026 (CVE-2026-33634); syft, which
  writes GORA's SBOM, and Grype come from one vendor, and Grype reads that SBOM.
  *Amended 2026-11-07:* the scan of a pull request runs with no network, from GORA's own
  scanner image, which carries the database; see the entry of that date. The scheduled run
  scans with the newest database, as a warning and not as a gate.
- **The updater.** A weekly workflow runs apt in the pinned base against the archive's
  latest imports, reads the candidate git, and opens one pull request that moves both
  imports, the lock and `GIT_VERSION` together; apt checks the signatures, as the build
  does. A pull
  request opened with a workflow's `GITHUB_TOKEN` starts no workflow, so it runs as a second
  App, `gora-updater` (contents and pull requests, this repository only), never
  `gora-release`, which bypasses the creation rulesets. The pins of cosign, syft, buildx and
  crane are not its business.

### 2026-11-05 — GORA's own base image, built from the same snapshot, rarely

**Why.** Every input of the release image is pinned by hash, so trust is done; availability is
not. Each build fetched from four services: Docker Hub (the `python` base), snapshot.debian.org
(git and the packages it depends on), PyPI (`uv.lock`) and GHCR (uv). On 2026-11-04 and
2026-11-05 snapshot.debian.org answered `503 first byte timeout`, `503 Backend fetch failed`
and `504 Gateway Timeout`, and every image build failed, on `main` after four merges. The
entry of 2026-10-20 said the build depends on the snapshot as it depends on PyPI; it does, and
a release image that can be built only when a third party answers is not one GORA can rebuild
on demand.

**Decision.** GORA keeps a base image of its own: Debian, Python and git, and nothing of GORA.
`deployments/docker/base.Dockerfile` starts from the same `python:3.12-slim-trixie` digest
the release Dockerfile pins, checks `PYTHON_VERSION` as the release Dockerfile does, and
installs `git=$GIT_VERSION` from the snapshot `debian.sources` names, checked against
`debian.lock`: the same steps and the same checks, moved, not rewritten. The image carries
`org.opencontainers.image.source` and the two snapshot ids it was built from. Apt retries a
failed download ten times (`Acquire::Retries=10`) and times out an HTTP or HTTPS connection
after 60 seconds (`Acquire::http::Timeout`, `Acquire::https::Timeout`), in this Dockerfile and
nowhere else: the base is built rarely, and the release image is built on every change.
*Amended 2026-11-07:* the release Dockerfile no longer pins that digest or checks
`PYTHON_VERSION`: it starts from the base, which declares both.

**Where it lives.** `ghcr.io/gora-tools/gora-base`, as one image index for linux/amd64 and
linux/arm64, whose digest is its identity. Nothing names it by tag: the only tag is
`run-<run id>-<attempt>`, which a registry needs to keep an index and no one reads.

**Who rebuilds it.** A person, by starting `.github/workflows/base.yml` on `main`, when the
`python` digest, the snapshot or `GIT_VERSION` moves. The workflow refuses any other ref, and
no event starts it. It builds each platform on its native runner, with no cache and
BuildKit provenance (`mode=max`), as the release image is built; smokes each platform (the
interpreter is `PYTHON_VERSION`, `/usr/bin/git` belongs to the package `git=$GIT_VERSION`, and
`git --version` prints its upstream version) in a registry on the runner; and only then does
one job, the only one that may write packages, move those images, unchanged, to GHCR by
digest and assemble the index. It prints the index digest as its result. `GITHUB_TOKEN`
pushes it; no GitHub App is involved. If an anonymous pull of the digest is refused, a person
makes the package public, and a person puts the digest in the release Dockerfile. An updater
that runs the workflow and moves the digest is not built.

**What is in force.** `tests/unit/test_build_pins.py` holds `base.Dockerfile` to the checks the
release Dockerfile has (pinned by digest; one exact git by one `apt-get`, from the sources and
under the lock), to the apt retries and timeouts above, to a scope of Debian, Python and git,
and, until the release image starts from it, to the same `PYTHON_VERSION`, `GIT_VERSION` and
`python` digest as the release Dockerfile; and holds `base.yml` to a trigger that is
`workflow_dispatch` alone, a first job that exits 1 unless the ref is `refs/heads/main` and
that every other job waits for, a write permission for the publishing job alone, and pushes
by digest. `scripts/gate/limits.py` keeps the last green run of each job of `base.yml`, and
allows none, as it does for the release workflow. The release image does not yet start from
the base; the pull request that makes it so removes the declarations and the `apt-get` from
the release Dockerfile, and with them the agreement test.

*Amended 2026-11-07:* that pull request is the entry of that date. The agreement test is gone
with the declarations it compared.

*Amended 2026-11-07 (the scanner entry below):* the workflow is no longer `base.yml` alone.
`base.yml` is a caller of the reusable workflow `own-image.yml`, which builds the base image
and the scanner image alike; `base.yml` holds the trigger (`workflow_dispatch` alone), its
concurrency group and the call, and `own-image.yml` holds the guard, the build, the smoke and
the push. The statements above about `base.yml` hold of the pair: the trigger of the caller,
the guard, the permissions, the push by digest and the limits of the jobs of the reusable
workflow. `scripts/gate/limits.py` keeps the last green run of each job, as it does for the
release workflow, and allows none until the workflow has run; it takes those of the called
jobs from the runs of the two callers (the entry below says how).

The main-only guard is a step of `own-image.yml` (before 2026-11-07, of `base.yml`), which
reads the ref of the caller's run, so a writer can run a changed copy of the workflow from a
branch: it holds against a mistake, not against a writer. The release image
names a base only by a digest that a reviewed pull request moves. The proof that a base was
built from `main` is its signature, decided with the builder's reusable workflow `build.yml`
and not built (release-model section 13).

### 2026-11-07 — the release image starts from the base, by digest; the Debian files leave its inputs

**Decision.** The build stage and the runtime stage of `deployments/docker/Dockerfile` both
start `FROM ghcr.io/gora-tools/gora-base@sha256:<digest>`, the index `base.yml` printed. The uv
stage stays as it is. No Docker Hub image and no package install remain in the release
Dockerfile, so a build of the release image reaches GHCR and PyPI and nothing else.

**One declaration per fact.** `PYTHON_VERSION`, `GIT_VERSION` and the Debian files
(`debian.sources`, `debian.lock`) are declared in `base.Dockerfile` alone.
`scripts/gate/versions.sh` reads the Python there and the uv in the release Dockerfile; the
Makefile reads `GIT_VERSION` there. `make image-smoke` still checks the git package and the
interpreter in the release image, so a base that does not hold what `base.Dockerfile`
declares fails the smoke test.

**The artifact's inputs (L8).** `artifacts/gora/artifact.yaml` no longer lists `debian.sources`
and `debian.lock`: nothing of the release image's build reads them. What the image is built
from is the base, and the digest that names it is a line of `deployments/docker/Dockerfile`,
an input: moving the digest is a change of an input and makes a candidate; rebuilding the base
changes none until the digest moves. `artifacts/gora/artifact.yaml` is a release file, never
an input (L8): editing its list makes no candidate, and no law changes.

**Who moves the base.** Dependabot keeps proposing the digest of `python:3.12-slim-trixie` in
`base.Dockerfile`, and does not touch the base reference, which has a digest and no tag. A base
bump is applied by a person running `base.yml` on `main` and moving the digest in the release
Dockerfile in a pull request. An updater that does both is not built.

**What is in force.** `tests/unit/test_build_pins.py` holds that the release Dockerfile has no
FROM but the uv stage and `ghcr.io/gora-tools/gora-base@sha256:<64 hex>`, runs no apt or
dpkg, and declares neither the Python, the git nor a Debian file; that `base.Dockerfile` is
the only Dockerfile with an apt step; that `versions.sh` takes the Python from the base and
reads none from the release Dockerfile; and that Dependabot ignores the base reference. The
agreement test of the entry of 2026-11-05 is removed with what it compared.

### 2026-11-07 — the image scan runs from GORA's own scanner image, with its database in it

**Why.** The entry of 2026-10-20 decides that Grype scans the release image of every pull
request and fails on a fixable high or critical vulnerability. Grype downloads its
vulnerability database on every run by default. Each build would then depend on Anchore's
distribution service, and the verdict on a pull request would change from one day to the next
for the same commit: a fix published upstream overnight would turn every open pull request red,
related to the image or not.

**Decision.** The database is a pinned input of the gate, as the base image is an input of the
build.

- **The scanner is GORA's own image,** `ghcr.io/gora-tools/gora-scanner`: Grype's image, by the
  digest of its index, and the database downloaded when GORA's image is built, whose checksum
  Grype checks against the one its listing publishes. One digest pins the tool and the data
  that were tested together, which matters because the database schema is tied to the Grype
  version.
- **A person builds it, from `main` only,** with the workflow that builds the base image, and
  it is pushed to GHCR by digest. It is a build input: it changes no byte of the release image,
  so L8 does not apply. A gate names it by digest.
- **A pull request is scanned with no network.** Grype's database update, its database age
  check and its check for a newer Grype are off in the image. Freshness is not a property of a
  pull request but of the digest, which a pull request moves, by hand until the updater
  exists. New findings appear in the pull request that moves the digest, beside their fix or
  an exception, and in no other.
- **A scheduled run scans with the newest database,** as an early warning and not as a gate.
- **Weighed and not taken.** The live database, failing closed: each build depends on Anchore,
  and a pull request goes red for a reason unrelated to its change. The database archive
  pinned apart from the tool: two pins that can drift, where the schema is tied to the Grype
  version. A scan of each pull request against `main` that fails only on what is new: two scans,
  and the database still live.

**Grounds.** Anchore's documentation lists the settings that make this possible: the database
update (`db.auto-update`), its age check (`db.validate-age`, "ensure db build is no older than
the max-allowed-built-age") and the address it downloads from (`db.update-url`), at
<https://oss.anchore.com/docs/reference/grype/configuration/>; the guide says to set
`db.validate-age: false` to disable the age validation
(<https://oss.anchore.com/docs/guides/vulnerability/database/>). The pinned Grype's own
`grype config` prints the same settings with their environment variables, and `grype db`
lists `import` among its commands (measured at v0.121.2). A scanner's database hosted on GHCR
has failed CI broadly before: in October 2024 the Trivy database hit GHCR's rate limits, and a
Trivy maintainer wrote that "currently, the only ways are to use [ECR Public] ... or self-host
DBs on another registry"
(<https://github.com/aquasecurity/trivy/discussions/7668>, 2024-10-08). OSV-Scanner separates
the scan of a pull request from the scheduled one: the first "will only report new
vulnerabilities introduced through the pull request", the second "will scan your project on a
set schedule and report all known vulnerabilities"
(<https://google.github.io/osv-scanner/github-action/>).

**The image** (`deployments/docker/scanner.Dockerfile`).

- It starts from Grype's image, `ghcr.io/anchore/grype:v0.121.2`, by the digest of its index.
  Anchore publishes the same index, with the same digest, on GHCR and on Docker Hub (measured
  2026-11-07), for linux/amd64, linux/arm64, linux/ppc64le and linux/s390x. GHCR is the
  one taken: the same bytes, and GHCR is the registry the build already reaches for GORA's
  own images and for uv, so the scanner's build reaches no registry more. Both platforms GORA
  builds are in the index.
- The base is built from scratch (Grype and its CA certificates, no shell), so the database is
  downloaded by `RUN ["/grype", "db", "update"]` into `/grype-db` (`GRYPE_DB_CACHE_DIR`), and
  the next step, `grype db status`, fails the build unless what is installed is valid.
- The environment turns off `GRYPE_DB_AUTO_UPDATE` ("check for database updates on
  execution"), `GRYPE_DB_VALIDATE_AGE` ("ensure db build is no older than the
  max-allowed-built-age") and `GRYPE_CHECK_FOR_APP_UPDATE` ("enable/disable checking for
  application updates on startup"), each quoted from `grype config` at the pinned version. The
  check of the database against its hash on each start (`GRYPE_DB_VALIDATE_BY_HASH_ON_START`)
  stays on.
- The fix filter applies before the fail threshold: at the pinned version, a package with an
  unfixed critical finding exits 2 with `--fail-on high`, and exits 0 with `--only-fixed
  --fail-on high` (measured on `libc6`, with no network). A finding with no fix therefore does
  not fail a pull request, which is the decision of the entry of 2026-10-20.
- `deployments/docker/scanner-data-sources.md` is copied into the image. It lists the data
  sources of the database as Anchore's page lists them
  (<https://oss.anchore.com/docs/reference/grype/data-sources/>). Neither that page nor the
  guide states a licence for any source or for the database, so the file gives each source's
  terms only where a page of the source itself was read: GitHub Security Advisories are
  CC-BY 4.0 (the advisory database's README). For the Debian Security Tracker its page says
  only that the data is publicly available, and NVD's pages returned no text when read; both,
  and every other source, are "not found", and none is stated from memory. Whether the GHCR
  package is public is a person's decision after the first run.
- The image's source is a label; its revision is the annotation the workflow sets, as for the
  base.

**The workflow.** One reusable workflow, `.github/workflows/own-image.yml`, builds GORA's own
images. `base.yml` and `scanner.yml` are its callers: `workflow_dispatch` alone, a concurrency
group each, the permissions the called jobs need, and one call that passes the Dockerfile, the
GHCR repository and the kind of image (`base` or `scanner`), which selects the smoke. The guard, the native builds without a cache, BuildKit
provenance, the smoke in a registry on the runner, the push by digest, `packages: write` in
the publishing job alone and the one tag of the index are those of the entry of 2026-11-05,
unchanged. The smoke is `scripts/gate/own-image-smoke.sh`: for the base, the checks the
workflow held; for the scanner, with `--network none` and a read-only root file system, the
Grype version and the status of the database, the scan of a package with a known fixed
vulnerability (`pkg:pypi/certifi@2026.6.17`, GHSA-6q48-6c7w-9gw2, fixed in 2026.10.18), which
must exit 2 and report it, and of its fixed version, which must exit 0.

**What is in force.** `tests/unit/test_build_pins.py` holds `scanner.Dockerfile` to one base by
tag and digest, the download and the status check, the database's directory, and the three
settings that keep it offline; holds both callers to a `workflow_dispatch` that is the only
trigger, a group of their own and one call with its inputs; holds the reusable workflow to the
statements of the entry of 2026-11-05; and runs the smoke script against a stand-in for docker
to show that each of its checks can fail. `scanner.Dockerfile` and its data-sources file are
gate-defining (ADR-016, rule 7). `scripts/gate/limits.py` takes the called jobs' limits from
`own-image.yml` and their records from the runs of its callers. `base.yml` and `scanner.yml`
are in its table of runs as workflows a person starts, with the last green run of each;
`own-image.yml` has no run of its own and no entry. A run of a caller shows a called job as
`<caller job> / <called job>` (`image / build (linux/amd64)`), and the tool records it under
the reusable workflow's job (`own-image.yml:build`); a run from before the workflow was a
caller shows the same job by its own name, and is recorded the same way. A name that starts
with a caller job's `<caller job> / ` and matches no job of the reusable workflow (a job
renamed there, still shown under its old name by the callers' last runs) is skipped and said,
like any job a workflow no longer has; the run's other jobs are recorded. A record of a called
job is held to its 10x like any other, and the file
keeps one for each caller and job. A reusable workflow whose callers are all in the table
may have no record until they have run.

**Not built.** The scan of the release image and of `uv.lock`, the scheduled run, and the
updater that runs `scanner.yml` and moves the digest (release-model section 13). No gate names
the scanner image yet.
